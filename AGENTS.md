# Project workflow

- Before managing GitHub issues, projects, branches, or PRs, read `/Users/sandersouza/Library/Mobile Documents/com~apple~CloudDocs/obsidian/personal/codex-instructions/github-instructions.md`. Treat that note as the authoritative GitHub workflow; if unavailable, report it instead of silently substituting these summary rules.
- Keep repository documentation, issue bodies, and code in English. Discuss work with the user in their preferred language.
- Preserve experiment learning in docs/, not raw experiment archives: document the problem, mechanism, rejected approaches, measured result, limits, source owner and reproduction command. Comment code blocks with their purpose and ordering invariants; public includes/helpers must state inputs/outputs, register/IFF clobbers, hardware/mapping ownership, scratch lifetime and reuse constraints. Keep inline contracts and modules/contracts.json synchronized. Documentation-only edits must preserve ROM bytes/symbol values and leave no large generated evidence behind.
- Publish the playable ROM as `dist/newrallyx.rom` with `dist/manifest.json`; run that exact file. Keep test/diagnostic/legacy variants in named `dist/` subdirectories, intermediates in `references/build/game*`, pinned caches in `references/cache/`, and emulator sessions in `references/sessions/`. Do not restore provisional `test-roms`, `fixed-hud.rom` or capability suffixes in normal build/run output. Disk space is constrained: retain compact results, hashes and workbooks in docs/, then delete raw builds, traces, videos, logs and per-issue artifacts. Do not create bulky archives or preserve disposable binaries by default. make clean must clear generated reference data while preserving contributor inputs, documented results and dist/.
- Before creating any GitHub issue, write its complete body to `.github/issues/<descriptive-slug>.md`.
- Publish issue bodies with `gh issue create --body-file <path>` or an equivalent structured API. Never put long prose in shell commands. Use Markdown files for issue, PR, and comment bodies.
- When the user asks to work on an issue, use the current chat where the request was made. Do not create or fork a separate chat unless explicitly requested. Read the issue URL, scope, acceptance criteria, and relevant decisions before acting. Creating backlog issues alone does not authorize implementation.
- Never commit original ROMs, extracted assets, disassembly, or fixtures containing original game data. Keep original ROMs and disassembly under ignored `references/`; keep active extracted/converted game assets under ignored `assets/arcade/` (and the approved wordmark in `assets/namco-title-56x8.png`). Temporary `references/assets/` copies must be removed after verified conversion. Commit tools, documentation, metadata, and synthetic fixtures only.
- Use contributor-supplied ROMs. Tools must not download or redistribute game ROMs.
- Preserve original asset dimensions at 1:1 scale. Target 256x212 by reducing the maze viewport and rearranging the HUD/radar, while preserving world coordinates and game rules.
- Preserve current quality, performance and stability: no reductions in graphics, colors, complete car drawings, HUD, audio, input or presentation behavior. Earlier exploratory permissions do not authorize regressions or timing concessions.
- Performance optimizations are authorized only with a demonstrated measured benefit, appropriate regression/stability tests, preserved quality and the strict2MiB ROM ceiling; keep64KiB compatibility. Target approximately30 presented gameplay FPS, report mean/tail/maximum costs and unchanged/slower cases honestly, and distinguish presentation from refresh/game-clock rates. Documentation/comment edits must preserve emitted ROM bytes and symbol values.
- ROM images must never exceed 2 MiB (2,097,152 bytes). There is no 4 MiB fallback. Preserve operation on unexpanded 64 KiB machines in the default build, including turbo work. The default cartridge detects mapper capacity and supported CPU acceleration. `MAPPER=1` only selects128KiB in openMSX; default/`MAPPER=0` select64KiB. Never use `MAPPER` to select a different ROM build or exported filename.
- Maintain a reproducible cycle ledger for rendering routines and hooks: workload, CPU/video configuration, ROM hash, calls per presented frame, inclusive and self cycles, mean/tail/maximum costs, synchronization waits, and remaining budget. Do not add inclusive parent and child costs together.
- Keep timing workbooks versioned under `docs/`. Maintain `docs/cycle-budget.xlsx` and its source ledger for the current measured ROM; run `make timing-workbook` after new relevant timing measurements. Preserve earlier workbooks under `docs/measurements/timing/archive/` with their original ROM hashes and workloads; never relabel an older measurement as current.
- Modularization is assembly-time source organization only. Preserve complete ROM bytes and all symbol values for matching configurations; run `make verify-module-layout` and document module API, register/IFF ownership, memory lifetimes and reuse limits. Do not add runtime wrappers, dispatch, calls, buffers, allocations, stack, mapper/VDP traffic, synchronization or frame latency for module boundaries.
- State refresh rate separately from gameplay/presentation rate. Keep full-frame, drawing-phase, and usable VBlank budgets distinct; treat an unverified 5,000-cycle VBlank reserve as a planning assumption, not a measured hardware limit.
- Short event pauses (for example flag capture) may be explored as bounded scheduling opportunities. Record their duration, deferred work, and worst-case cost, preserve input/game-rule consistency, and leave final perceptual acceptance to the user. Do not conceal recurring overload as an event pause.
- Prefer retaining original Z80 game logic and adapting hardware interfaces. Rendering and sound fidelity remain subject to measured feasibility.
- Keep the HUD enabled in new gameplay and performance test builds. Run HUD-off builds or comparisons only when the user explicitly requests them.
- Continue gameplay integration when sprite candidates exceed eight per scanline. Keep real hardware limits enabled and document any resulting culling; defer sprite optimization until it becomes a serious practical blocker. Preserve complete original car drawings.
- Do not push, commit, or implement backlog items unless requested. Keep unrelated user changes intact.

- First builds must be reproducible from contributor arcade ROMs in `references/roms/nrallyx/`. Normal `make build`/`make run` must prepare missing canonical assets automatically before either presenter links; retain explicit idempotent `make extract-all`, `make extract-graphics`, `make extract-scenes` and `make extract-native` commands. Test the absent-asset path, not only warm caches. Keep `assets/arcade/**` and all reference payloads ignored; publish only empty reference `.gitkeep` markers.
